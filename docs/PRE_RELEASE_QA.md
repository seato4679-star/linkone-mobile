# 公開直前QAレポート

実施日: 2026-09-22。対象: LinkOne Mobile。Windows / Node.js 24.16.0 / npm 11.13.0、Next.js 16.3.5 / React 19.3.0。本番ビルドを `npm run start` で起動し、実ブラウザとHTTPテストで確認した。

## 2026-09-24 Claude Codeレビューへの対応

- `/privacy`に、公開者が確定させる連絡先・保存期間のTODOを追加。削除依頼は権限を持つ運営者がSupabase SQL Editorで処理する運用をREADMEへ記載した。
- Supabaseのlegacy JWT形式キーにだけ`Authorization`を付与し、新形式の`sb_secret_...`キーは`apikey`のみで送るようにした。実Supabase接続は引き続き公開前に確認する。
- DB障害の503では二重申込を避ける案内を表示し、管理一覧のClient Componentにはメールアドレス・電話番号を渡さない。
- 氏名の文字数判定、Vercel向けIPヘッダー、CSP/HSTS、申込選択欄のサーバーエラー表示とフォーカスを改善した。未使用の一覧GET APIを削除した。
- 2026-09-24に`npm run review:check`（lint・typecheck・単体テスト7件・build）と、`TEST_BASE_URL=http://127.0.0.1:3001 npm run test:smoke`（ローカルデモ49件）へ合格した。3001番ポートは既存の3000番開発サーバーとレート制限状態を分離するために使用した。

## 公開可能か

**NO — 現在の設定のまま、申込・保存・管理まで動作する完成版としてVercelへ公開する段階ではない。**

画面とローカルデモの一連の処理は修正・再検証済み。ローカルでの作品説明には使用できる。一方、Supabase URL / service_roleキーは未設定で、実DBの構築・読み書きとVercel上のHTTPS動作は未検証。本番設定と下記の公開チェックが済んだ段階で最終判定する。これは機能未実装と外部環境未検証を区別した判定である。

## セキュリティ確認

1. service_roleは`server-only`モジュールの環境変数から読み、ブラウザへ渡さない。NEXT_PUBLICは使用していない。
2. `.env.local`と`.local/`はGit対象外。既存Git履歴は0コミットで、履歴内に秘密が混入していた状態ではない。未追跡ファイルがあるため公開者が初回コミットを行う。
3. ブラウザ用JavaScript 16ファイルに、サービスキー変数名やサンプル認証値がないことを検査。実Supabaseキーは未設定なので、その実値を使った漏えいテストは行っていない。
4. 未認証の一覧・更新APIを401で拒否。詳細はログインへ遷移し、個人情報を含まない。署名改ざんと余分なCookie区切りも拒否。
5. API側でも入力検証し、ID・状態・料金などの追加フィールドを信用しない。Content-Type、8KB上限、Originを検証。
6. 管理CookieはHttpOnly / SameSite=Strict。受付CookieはHttpOnly / SameSite=Lax / Path=/complete、1時間。HTTPSまたはVercelではSecure。実VercelのCookie挙動は公開前確認が必要。
7. DBエラーは一般的な503応答へ変換し、秘密やDB内部情報を返さない。DB未設定時にローカルファイルへ書き込まないことを実測。
8. SQLには主キー・NOT NULL・CHECK・default・RLS・ブラウザ向けロールの権限取消しがある。SQLを実Supabaseへ適用した結果は未検証。
9. `npm audit --omit=dev --audit-level=high`で本番依存の既知脆弱性0件。実施時点の結果で、将来の安全性を保証しない。

## Vercel公開前に行うこと

1. 自分のGit著者情報・remoteを設定し、`.env.local`や`.local`を含めず初回コミット・pushする。`git status`と公開リポジトリの内容を確認する。
2. Supabaseにデモ専用DBを作り、`supabase/schema.sql`を新しいDBへ実行する。既存DBに破壊的な変更として実行しない。
3. 独自のADMIN_PASSWORDとランダムなSESSION_SECRETを準備する。サンプル値のままでは公開環境で拒否される。
4. Vercelの必要なPreview / Production環境に、`DEMO_MODE=false`とSupabase URL・service_roleキー・独自の認証設定を登録する。legacy JWT形式と新形式の`sb_secret_...`キーのどちらも対応する。キーへNEXT_PUBLICを付けない。
5. `/privacy`へ実際の連絡方法と保存期間を記載し、架空情報だけで試すルールを維持する。
6. Next.js、Node.js 24.x、`npm run build`の構成でまずPreviewへデプロイする。
7. HTTPSのPreviewで架空の申込を1件作成し、Supabase Table Editorと管理詳細で同じID・全項目・日時を確認。状態更新もDB上で確認する。
8. 未ログインで個人情報を取得できないこと、ブラウザのJavaScript/HTML/応答に秘密がないこと、Console・Networkに想定外の失敗がないことを確認してから公開する。

## 公開後に確認すること

- 本番URLでLP→公式→料金→試算→申込→完了→管理の一巡を行う。
- PCと実スマホで文字・メニュー・入力・表を確認。iOS Safariを含める。
- 本番URLのOriginでPOST/PATCHが通り、別Originが拒否されることを確認。
- CookieのSecure/HttpOnly、8時間の管理期限、1時間の受付期限、ログアウト後の拒否を確認。
- Supabaseに保存されること、Vercel再起動・再デプロイでもデータが残ることを確認。
- 503・429や大量の申込を監視。プロセス内回数制限だけを公開環境の防御として過信しない。
- VercelとSupabaseのログに実個人情報や秘密情報を出さず、デモデータを宣言した期間に合わせて管理する。

## 学習用: 今回の重要コード

```tsx
<fieldset disabled={pending} className="form-layout form-fields">
```

`application-form.tsx`のこの1行は、API応答を待つ間、内側の入力と送信を一括で無効にする。画面表示のStateに加え、`submitting.current`が連続イベントを防ぐ。

```ts
sessionSecret();
const application = await createApplication(result.data);
```

`api/applications/route.ts`では、1行目で署名設定を検証してから、2行目で保存する。保存してから設定不備に気づく順序にしない。

```ts
.update(`receipt:${payload}`)
```

`receipt.ts`のこの行は、受付IDと有効期限を受付用の用途識別子と一緒にHMACへ渡す。HMACは秘密鍵で改ざんを検知する仕組みであり、暗号化ではない。受付IDを知るだけでは署名を作れない。Cookieはブラウザがサーバーへ自動送信する情報で、HttpOnlyはページのJavaScriptから読ませない設定。

詳しい全体の流れは [REQUEST_FLOW](REQUEST_FLOW.md)、初学者向け用語は [LEARNING_GUIDE](LEARNING_GUIDE.md) を参照。

## 採用担当者・エンジニアが見やすい点

最初はHeroの説明、料金の読みやすさ、スマホの完成度、申込まで迷わないかが見られる可能性が高い。エンジニアには、選択値がAPI・保存・管理で一致すること、ブラウザとサーバーの責務、エラー処理、秘密情報の扱い、テストと説明資料が判断材料になる。

一方、実DB未検証のまま「完成」と説明すること、共有パスワードを本格認証と説明すること、推薦機能がないのに推薦と説明することは信頼を損ねる。公開前の外部環境確認を終え、デモの範囲と実装理由を自分の言葉で説明できる状態にする。共通部品・型・API・SQLを順に追える構成は、その説明に使える。
